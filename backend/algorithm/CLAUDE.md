# 프로젝트 규격 문서 (v2)

> [변경] = v1에서 바뀐 곳, [추가] = 새로 넣은 곳, [결정 필요] = 아직 미정

## 1. 공통 단위·표기
- 길이: m (소수점 3자리)
- 각도: degree (도)
- 시간: ISO 8601, 한국시간 (예: `2026-10-05T14:30:00+09:00`)
- 날짜: `YYYY-MM-DD`
- 일사량: W/m², PPFD: μmol/m²/s, DLI: mol/m²/day
- JSON 키: snake_case (예: `room_id`, `total_dli`)
- 상태값(enum): 대문자 (예: `SKY`, `LOW`)

## 2. 방위각·고도각 기준 (스캔, 태양, 방 방향 모두 동일)
- 방위각(azimuth): 진북 0°, 시계방향 증가, 0~360 (동 90, 남 180, 서 270)
- 고도각(elevation): 수평선 0°, 천정 90°
- 자북이 아니라 진북 기준. 센서 값은 앱에서 진북으로 변환해서 보냄. 디버그용으로 자북 원본값도 같이 저장
- **[변경]** 변환식: `진북 = 자북 + 편각` (편각: 동쪽 +, 서쪽 −). 1차는 한국 중부 근사값 편각 **−8.7°** 고정 (오차 약 ±1°).
  필요하면 계산 쪽에서 Room 위경도로 편각을 다시 계산해 자북 원본값으로 재보정 가능
- **[추가]** 앱(창밖 스캔)과 ARCore(`x_axis_azimuth_deg`) 모두 같은 편각 −8.7°를 사용
- pvlib 태양 위치 출력과 같은 기준이라 변환 없이 바로 비교 가능

## 3. 방 좌표계
- 원점: 방 바닥 모서리 중 하나 (RoomCorner `order_index` 0번)
- X축: 0번 모서리에서 1번 모서리 방향 (가로)
- Y축: 위쪽 (높이), 바닥이 y=0
- Z축: 바닥면에서 X축과 수직이고 방 안쪽 방향 (세로)
- **[추가]** 오른손 좌표계 (ARCore와 동일)
- 방 내부는 항상 x≥0, z≥0
- **[변경]** 방 모서리 저장: 바닥 모서리만, 위에서 내려다볼 때 "시계방향"으로 0, 1, 2, 3 순서
  (오른손 좌표계 + Z가 방 안쪽이면 반시계가 아니라 시계방향이 됨). 천장 높이는 `Room.height_m`에 따로 저장
- 1차는 직사각형 방(모서리 4개)만 지원
- `Room.x_axis_azimuth_deg`: X축(0→1번 모서리 방향)이 가리키는 방위각(진북 기준). 태양 계산에 필수
- **[추가]** Z축 방위각 = `x_axis_azimuth_deg + 90°`
- **[추가]** `x_axis_azimuth_deg` 측정: B가 ARCore 측정 중 나침반(자력계) 값을 같은 시점의 카메라 방향과 함께 여러 번 기록해
  평균 → 진북 변환(편각 −8.7°)해서 저장
- `Room.latitude`, `Room.longitude`: 태양 위치 계산용 위도·경도
- **[추가]** 위경도: 앱에서 사용자가 지역을 입력 → 백엔드가 위경도로 변환해 Room에 저장
- **[결정 필요]** `backend` 브랜치 `docs/DATA_CONTRACT.md`(실제 Android 앱 저장 규격 기준)와 이 문서의 좌표계
  가정이 다름: 이 문서는 "0→1번 모서리 방향으로 축을 회전해서 저장(그래서 항상 x≥0,z≥0)"을 가정하는데,
  실제 앱은 "AR 세션 시작 시점 방향을 그대로 쓰고 첫 벽 방향으로 회전하지 않음"(2번째 모서리 z가 0이
  아닐 수 있고 음수 x,z도 정상)이라고 명시함. `a_grid.py`의 격자 생성(`width_m`/`depth_m` 기반 단순
  사각형 가정)이 실제 앱 데이터와 안 맞을 수 있음 — 현재는 보류, 추후 반영 여부 결정 필요

## 4. 창문 4꼭짓점 순서
- 방 안에서 창문을 바라봤을 때 기준
- 0: 좌하 → 1: 우하 → 2: 우상 → 3: 좌상
- 좌표는 방 좌표계 (x, y, z)
- **[변경]** 바깥 방향 법선 = `(V3 − V0) × (V1 − V0)`
  (`(V1 − V0) × (V3 − V0)`는 오른손 좌표계에서 방 "안쪽"을 향함)

## 5. 격자 규격
- 1차 기본값: 20×20 (rows × cols)
- col은 X 방향, row는 Z 방향
- 인덱스는 `[row][col]`, 0부터 시작
- 셀 중심 좌표: `x = (col + 0.5) × 방 가로 / cols`, `z = (row + 0.5) × 방 세로 / rows`
- 계산 높이: y = 0 (1차는 식물 높이 미고려)
- 식물 위치(Plant)는 격자 인덱스 `{row, col}`로 저장. 위치 중복 체크도 이 기준

## 6. 창밖 스캔 규격
- 범위: 창문 바깥 방향 기준 좌우 90°씩 총 180°, 15° 간격으로 약 13장
- **[추가]** 촬영 자세: 휴대폰을 수평 기준 약 30° 위로 든 상태. 앱이 안내 문구와 현재 각도를 보여주고,
  목표 각도 30° ±5°를 벗어나면 경고
  (세로 화각 약 70° 기준으로 고도 약 −5°~65°가 한 번에 찍힘. 수평선(0°)이 항상 사진에 들어가도록 여유를 둔 값)
- 사진: JPEG, 세로(portrait) 고정, 긴 변 1280px, EXIF 회전 적용된 상태로 저장
- 피치: 수평 0°, 위를 보면 +
- 롤: 수평 0°, 시계방향으로 기울면 +
- **[추가]** 화각(hfov/vfov)은 기종마다 다르므로(약 65~75°) 고정값을 쓰지 않음. 앱이 사진 EXIF의 초점거리로 계산해서 보냄
- 이미지는 파일로 저장하고 DB에는 경로만 저장
- 가능하면 창문을 열고 촬영 (유리 반사 방지)

## 7. SKY/NON-SKY 결과 규격
- 1° 간격 격자. 방위각 0~359 (360칸), 고도각 0~90 (91칸)
- 배열 인덱스는 `[elevation][azimuth]`
- 값: 1 = SKY, 0 = NON-SKY, -1 = 촬영 안 된 영역
- **[변경]** -1 처리 규칙:
  - 그 방위각에서 실제로 찍힌 최고 고도보다 위쪽의 -1 → SKY로 처리
    (NON-SKY로 두면 해가 높은 4~8월 한낮 직사광이 전부 0이 됨. 창문 통과 여부는 Ray 검사에서 따로 판정)
  - 그 외 -1 (스캔 180° 범위 밖 좌우 등) → NON-SKY로 처리
- **[추가]** `max_captured_elevation_deg`: 방위각별 실제로 찍힌 최고 고도 (360칸, 촬영 안 된 방위각은 -1). 위 규칙과 오차 분석에 사용
- 태양 위치 조회: `sky[round(고도)][round(방위각) % 360]` (-1이면 위 규칙 먼저 적용)

```json
{
  "scan_id": 1,
  "az_step_deg": 1,
  "el_step_deg": 1,
  "max_captured_elevation_deg": [...360개...],
  "sky": [[...360개...], ...91줄...]
}
```

## 8. 태양 계산 시점
- NREL SPA (pvlib, `method='nrel_numpy'`)
- 08:00~18:00, 10분 간격, 61시점, 한국시간
- 고도각 0° 이하인 시점은 제외
- **[추가]** 08~18시는 1차 단순화. 여름(일출 약 05시, 일몰 약 20시)에는 DLI가 실제보다 작게 나올 수 있으며,
  실측 검증 후 일출~일몰 전체로 확장 여부 결정
- **[결정 필요]** `backend` 브랜치 `docs/WEATHER_API.md`: 일사량(DNI/DHI)은 매시 정각 값이 `PRECEDING_HOUR_MEAN`
  (그 시각까지 지난 1시간 평균)이라고 명시하고, "평균을 순간값으로 간주해 선형 보간하면 오차 생김 — C가
  평균 구간을 보존하는 분배/보간 정책을 정해야 함"이라고 못박아둠. 지금 `b_solar.py`는 순간값 선형보간
  (`interpolate(method="time")`)만 씀 — 현재는 보류, 추후 반영 여부 결정 필요

## 10. 진단·추천 결과 JSON (Recommendation)
- status: OK(적정) / LOW(부족) / HIGH(과다)
- 판정 기준: `total_dli < min_dli`이면 LOW, `total_dli > max_dli`이면 HIGH, 그 사이면 OK
- 현재 위치가 OK면 `recommended`는 null (유지)
- 식물끼리 추천 위치 중복 불가
- **[결정 필요]** `score`(0~1) 계산식: C가 정해서 여기에 한 줄로 적기 (예: 요구 DLI 범위 중앙값과의 차이 기반)
- **[결정됨]** 가구 등 식물을 놓을 수 없는 칸: 프론트가 요청에 `blocked_cells` `[{row, col}]`를 보내면 추천 후보에서 제외 (①번으로 확정)

```json
{
  "room_id": 1,
  "date": "2026-10-05",
  "plants": [
    {
      "plant_id": 3,
      "species_id": 12,
      "required_dli": { "min": 10.0, "max": 20.0 },
      "current": { "row": 4, "col": 7, "total_dli": 6.32, "status": "LOW" },
      "recommended": { "row": 15, "col": 3, "total_dli": 14.80, "score": 0.92 }
    }
  ]
}
```

## 11. API 공통 규칙
- REST, 경로 앞에 `/api/v1` (예: `/api/v1/rooms/1/windows`)
- 요청·응답: JSON, 이미지 업로드만 `multipart/form-data`
- 인증: 로그인하면 JWT 발급, 요청 헤더에 `Authorization: Bearer {token}`
- ID: 정수 auto increment
- 에러: FastAPI 기본 형식 `{"detail": "메시지"}` + HTTP 상태코드 (400 잘못된 요청, 401 인증 실패, 404 없음)
- 모든 데이터는 `user_id`로 묶어서 본인 데이터만 조회 가능

## 12. 이름 규칙
- DB 테이블·컬럼: snake_case (`room_corner`, `order_index`)
- Python: snake_case / Kotlin·TypeScript: camelCase. API 경계에서는 snake_case JSON으로 통일
